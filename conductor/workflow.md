# 프로젝트 워크플로우

## 기본 원칙

1. **The Plan is the Source of Truth:** `plan.md`가 모든 작업의 기준입니다.
2. **The Tech Stack is Deliberate:** 기술 스택 변경 시 구현 *전에* `tech-stack.md`에 문서화해야 합니다.
3. **Test-Driven Development:** 기능 구현 전에 단위 테스트를 먼저 작성합니다.
4. **High Code Coverage:** 모든 모듈의 코드 커버리지 80% 이상을 목표로 합니다 (일시적 비활성화).
5. **User Experience First:** 모든 결정은 사용자 경험을 최우선으로 합니다.
6. **Non-Interactive & CI-Aware:** 비대화형 명령어를 선호합니다. `CI=true`를 사용하여 감시 모드 도구(테스트, 린터)가 한 번만 실행되도록 합니다.

## 태스크 워크플로우

모든 태스크는 엄격한 생명주기를 따릅니다:

### 버그 수정(Bug Fix) 워크플로우

1. **재현 테스트 작성:** 버그를 수정하기 전, 해당 문제를 확실히 재현하고 감지할 수 있는 견고한 **단위 테스트(Unit Test)** 또는 **DB 통합 테스트(Integration Test)**를 먼저 작성합니다.
2. **TDD 방식 적용:** 작성한 테스트가 실패하는 것을 확인한 후, 테스트를 통과시키기 위한 최소한의 코드를 수정합니다.
3. **회귀 방지:** 수정 후 모든 관련 테스트를 실행하여 기존 기능에 영향이 없는지(Regression) 확인합니다.

### 표준 태스크 워크플로우

1. **태스크 선택:** `plan.md`에서 순서대로 다음 작업할 태스크를 선택합니다.

2. **진행 중 표시:** 작업 시작 전 `plan.md`에서 해당 태스크를 `[ ]`에서 `[~]`로 변경합니다.

3. **기능 구현:**
   - 태스크 명세에 따라 코드를 작성합니다.
   - 작성 중에는 `minglit_kit`의 디자인 토큰과 프로젝트의 코드 스타일 가이드를 철저히 준수합니다.

4. **코드 품질 강화 (Zero-Warning 루프):**
   - 구현 완료 후 다음 명령어를 순차적으로 실행하여 코드를 정제합니다. **중요:** 에러뿐만 아니라 모든 '경고(Warning)'와 '정보(Info)'를 제거해야 합니다.
     1. **자동 수정:** `dart fix --apply` (MCP `dart_fix` 사용)
     2. **포맷팅:** `dart format .` (MCP `dart_format` 사용)
     3. **정적 분석:** `flutter analyze` (MCP `analyze_files` 사용)
   - **반복:** `flutter analyze` 결과가 "No issues found!"가 될 때까지 코드를 수정하고 루프를 반복합니다.
   - **빌드 검증:** 각 앱(`apps/app_partner`, `apps/app_user`)에서 `flutter build apk` 또는 `flutter build ios` (가능한 경우)를 실행하여 빌드 오류가 없는지 확인합니다. 최소한 `flutter build web` 또는 `flutter build bundle`로 컴파일 가능성을 검증해야 합니다.
   - **수동 검증:** 로컬 환경에서 앱을 실행하여 기능이 기획대로 동작하는지 확인합니다.

5. **변경 사항 설명 및 리뷰 요청:**
   - **검증 루프:** 위 검증 단계(format, fix, lint, build)가 모두 통과했음을 확인합니다.
   - **설명:** 구현된 기능과 변경된 코드의 핵심 내용, 특히 디자인 토큰 적용 여부를 사용자에게 상세히 설명합니다.
   - **요청:** 사용자에게 변경 사항에 대한 리뷰를 요청하고, 커밋해도 되는지 명시적으로 허락을 구합니다. 승인을 **기다립니다**.

6. **문서화 (필요 시):** 구현이 기술 스택과 달라지는 경우:
   - 구현을 **중단**합니다.
   - `tech-stack.md`에 새로운 설계를 업데이트합니다.
   - 변경 이유를 설명하는 날짜가 포함된 노트를 추가합니다.
   - 구현을 재개합니다.

7. **코드 변경 커밋:**
   - **전제 조건:** 사용자의 최종 승인을 받았는지 확인합니다.
   - **CI/CD 보호:** 린트 경고나 빌드 오류가 있는 상태에서 절대 푸시하지 않습니다.
   - 태스크와 관련된 모든 코드 변경 사항을 스테이징합니다.
   - 명확하고 간결한 커밋 메시지를 제안합니다. 예: `feat(ui): implement event header section`.
   - 커밋을 수행합니다.

10. **Git Notes로 태스크 요약 첨부:**
    - **Step 10.1: Get Commit Hash:** 방금 완료한 커밋의 해시를 가져옵니다 (`git log -1 --format="%H"`).
    - **Step 10.2: Draft Note Content:** 완료된 태스크에 대한 상세 요약을 작성합니다. 태스크 이름, 변경 요약, 생성/수정된 파일 목록, 변경의 핵심 "이유"를 포함해야 합니다.
    - **Step 10.3: Attach Note:** `git notes` 명령어를 사용하여 요약을 커밋에 첨부합니다.
      ```bash
      # The note content from the previous step is passed via the -m flag.
      git notes add -m "<note content>" <commit_hash>
      ```

11. **태스크 커밋 SHA 기록:**
    - **Step 11.1: Update Plan:** `plan.md`를 읽고 완료된 태스크 라인을 찾아 상태를 `[~]`에서 `[x]`로 변경하고, *방금 완료한 커밋* 해시의 앞 7자리를 뒤에 덧붙입니다.
    - **Step 11.2: Write Plan:** 업데이트된 내용을 `plan.md`에 씁니다.

12. **플랜 업데이트 커밋:**
    - **Action:** 수정된 `plan.md` 파일을 스테이징합니다.
    - **Action:** `conductor(plan): Mark task 'Create user model' as complete` 형식의 설명적인 메시지로 커밋합니다.

### 페이즈 완료 검증 및 체크포인트 프로토콜

**Trigger:** `plan.md`의 페이즈를 마무리하는 태스크가 완료된 직후 실행됩니다.

1.  **Announce Protocol Start:** 페이즈가 완료되었으며 검증 및 체크포인트 프로토콜이 시작됨을 사용자에게 알립니다.

2.  **페이즈 변경 사항에 대한 테스트 커버리지 확인:**
    -   **Step 2.1: Determine Phase Scope:** 이번 페이즈에서 변경된 파일을 식별하기 위해 시작점을 찾습니다. `plan.md`에서 *이전* 페이즈 체크포인트의 Git 커밋 SHA를 찾습니다. 이전 체크포인트가 없다면 첫 커밋 이후의 모든 변경 사항이 범위입니다.
    -   **Step 2.2: List Changed Files:** `git diff --name-only <previous_checkpoint_sha> HEAD`를 실행하여 이번 페이즈에서 수정된 모든 파일 목록을 가져옵니다.
    -   **Step 2.3: Verify and Create Tests:** 목록의 각 파일에 대해:
        -   **중요:** 먼저 확장자를 확인합니다. 코드가 아닌 파일(예: `.json`, `.md`, `.yaml`)은 제외합니다.
        -   나머지 코드 파일에 대해 대응하는 테스트 파일이 존재하는지 확인합니다.
        -   테스트 파일이 없다면 **반드시** 생성해야 합니다. 테스트 작성 전, **먼저 리포지토리의 다른 테스트 파일을 분석하여 올바른 명명 규칙과 테스트 스타일을 파악하십시오.** 새 테스트는 이번 페이즈의 태스크(`plan.md`)에 기술된 기능을 **반드시** 검증해야 합니다.

3.  **DB 로직 검증 (해당 시):**
    -   페이즈에 DB 트리거, RLS, Edge Function 호출 등 백엔드 로직 변경이 포함된 경우, `tests/backend_integration` 패키지를 사용하여 통합 테스트를 작성하고 실행해야 합니다.
    -   테스트 파일은 `tests/backend_integration/src/<domain>/` 하위에 위치해야 합니다.

4.  **자동화 테스트 실행 및 주도적 디버깅:**
    -   실행 전, 사용할 쉘 명령어를 **반드시** 알립니다.
    -   **알림 예시:** "페이즈 검증을 위해 자동화 테스트 스위트를 실행하겠습니다. **명령어:** `CI=true npm test`"
    -   알린 명령어를 실행합니다.
    -   테스트가 실패하면 사용자에게 알리고 디버깅을 시작합니다. **최대 두 번**까지 수정을 제안할 수 있습니다. 두 번째 수정 후에도 테스트가 실패하면 **중단**하고, 지속적인 실패를 보고한 후 사용자의 지침을 구해야 합니다.

4.  **상세하고 실행 가능한 수동 검증 계획 제안:**
    -   **중요:** 계획을 세우기 위해 먼저 `product.md`, `product-guidelines.md`, `plan.md`를 분석하여 완료된 페이즈의 사용자 대면 목표를 파악합니다.
    -   필요한 명령어와 구체적인 예상 결과를 포함하여 사용자가 검증 과정을 따라할 수 있는 단계별 계획을 **반드시** 생성해야 합니다.
    -   사용자에게 제시하는 계획은 다음 형식을 **반드시** 따라야 합니다:

        **프론트엔드 변경 시:**
        ```
        자동화 테스트가 통과했습니다. 수동 검증을 위해 다음 단계를 따라주세요:

        **수동 검증 단계:**
        1.  **개발 서버 시작 명령어:** `npm run dev`
        2.  **브라우저 열기:** `http://localhost:3000`
        3.  **확인 사항:** 새로운 사용자 프로필 페이지가 보이고, 이름과 이메일이 올바르게 표시되는지 확인합니다.
        ```

        **백엔드 변경 시:**
        ```
        자동화 테스트가 통과했습니다. 수동 검증을 위해 다음 단계를 따라주세요:

        **수동 검증 단계:**
        1.  **서버가 실행 중인지 확인합니다.**
        2.  **터미널에서 다음 명령어 실행:** `curl -X POST http://localhost:8080/api/v1/users -d '{"name": "test"}'`
        3.  **확인 사항:** 상태 코드 `201 Created`와 함께 JSON 응답을 받는지 확인합니다.
        ```

5.  **명시적인 사용자 피드백 대기:**
    -   상세 계획을 제시한 후 사용자에게 확인을 요청합니다: "**기대하신 내용과 일치하나요? '예'라고 확인해주시거나 수정할 부분을 알려주세요.**"
    -   **일시 정지**하고 사용자의 응답을 기다립니다. 명시적인 '예' 또는 확인 없이는 진행하지 마십시오.

6.  **체크포인트 커밋 생성:**
    -   모든 변경 사항을 스테이징합니다. 변경 사항이 없다면 빈 커밋으로 진행합니다.
    -   명확하고 간결한 메시지로 커밋합니다 (예: `conductor(checkpoint): Checkpoint end of Phase X`).

7.  **Git Notes로 감사 가능한 검증 보고서 첨부:**
    -   **Step 8.1: Draft Note Content:** 자동화 테스트 명령어, 수동 검증 단계, 사용자의 확인 내용을 포함한 상세 검증 보고서를 작성합니다.
    -   **Step 8.2: Attach Note:** `git notes` 명령어와 이전 단계의 전체 커밋 해시를 사용하여 전체 보고서를 체크포인트 커밋에 첨부합니다.

8.  **페이즈 체크포인트 SHA 기록:**
    -   **Step 7.1: Get Commit Hash:** *방금 생성한 체크포인트 커밋*의 해시를 가져옵니다 (`git log -1 --format="%H"`).
    -   **Step 7.2: Update Plan:** `plan.md`를 읽고 완료된 페이즈 헤딩을 찾아 `[checkpoint: <sha>]` 형식으로 앞 7자리를 덧붙입니다.
    -   **Step 7.3: Write Plan:** 업데이트된 내용을 `plan.md`에 씁니다.

9. **플랜 업데이트 커밋:**
    -   **Action:** 수정된 `plan.md` 파일을 스테이징합니다.
    -   **Action:** `conductor(plan): Mark phase '<PHASE NAME>' as complete` 형식의 설명적인 메시지로 커밋합니다.

10.  **Announce Completion:** 페이즈가 완료되었고 체크포인트가 생성되었으며, 상세 검증 보고서가 git note로 첨부되었음을 사용자에게 알립니다.

### 품질 게이트

태스크 완료 표시 전 확인 사항:

- [ ] 모든 테스트 통과
- [ ] 코드 커버리지 요구사항 충족 (>80%) (일시적 비활성화)
- [ ] 코드가 프로젝트 스타일 가이드를 따름 (`code_styleguides/` 정의)
- [ ] 모든 공개 함수/메서드 문서화 (예: docstrings, JSDoc, GoDoc)
- [ ] 타입 안전성 강제 (예: type hints, TypeScript types, Go types)
- [ ] 린팅 또는 정적 분석 에러 없음 (프로젝트 설정 도구 사용)
- [ ] 모바일에서 올바르게 동작 (해당 시)
- [ ] 필요 시 문서 업데이트
- [ ] 보안 취약점 없음

## 코드 리뷰 프로세스

### 자가 점검 체크리스트
리뷰 요청 전:

1. **기능성**
   - 기능이 명세대로 작동함
   - 엣지 케이스 처리됨
   - 에러 메시지가 사용자 친화적임

2. **코드 품질**
   - 스타일 가이드 준수
   - DRY 원칙 적용
   - 명확한 변수/함수 이름
   - 적절한 주석

3. **테스팅**
   - 포괄적인 단위 테스트
   - 통합 테스트 통과
   - 적절한 커버리지 (>80%)

4. **보안**
   - 하드코딩된 비밀 정보 없음
   - 입력값 검증 존재
   - SQL 인젝션 방지
   - XSS 보호 적용

5. **성능**
   - 데이터베이스 쿼리 최적화
   - 이미지 최적화
   - 필요 시 캐싱 구현

6. **모바일 경험**
   - 터치 타겟 적절함 (44x44px)
   - 줌 없이 텍스트 읽기 가능
   - 모바일에서 허용 가능한 성능
   - 네이티브 앱 같은 상호작용

## 커밋 가이드라인

### Message Format
```
<type>(<scope>): <description>

[optional body]

[optional footer]
```

### Types
- `feat`: 새로운 기능
- `fix`: 버그 수정
- `docs`: 문서만 변경
- `style`: 포맷팅, 세미콜론 누락 등
- `refactor`: 버그 수정이나 기능 추가가 없는 코드 변경
- `test`: 누락된 테스트 추가
- `chore`: 유지보수 작업

### Examples
```bash
git commit -m "feat(auth): Add remember me functionality"
git commit -m "fix(posts): Correct excerpt generation for short posts"
git commit -m "test(comments): Add tests for emoji reaction limits"
git commit -m "style(mobile): Improve button touch targets"
```

## 완료 조건 (Definition of Done)

태스크 완료 기준:

1. 명세에 따라 모든 코드 구현됨
2. 단위 테스트 작성 및 통과
3. 코드 커버리지 요구사항 충족
4. 문서 완료 (해당 시)
5. 설정된 모든 린팅 및 정적 분석 검사 통과
6. 모바일에서 훌륭하게 작동 (해당 시)
7. `plan.md`에 구현 노트 추가
8. 적절한 메시지로 변경 사항 커밋
9. 커밋에 태스크 요약이 담긴 Git note 첨부

## 비상 절차

### 운영 환경의 치명적 버그
1. main에서 hotfix 브랜치 생성
2. 버그에 대한 실패하는 테스트 작성
3. 최소한의 수정 구현
4. 모바일 포함 철저한 테스트
5. 즉시 배포
6. plan.md에 기록

### 데이터 손실
1. 모든 쓰기 작업 중단
2. 최신 백업에서 복구
3. 데이터 무결성 검증
4. 사고 기록
5. 백업 절차 업데이트

### 보안 침해
1. 모든 비밀 정보(Secrets) 즉시 교체
2. 접근 로그 검토
3. 취약점 패치
4. 영향을 받은 사용자에게 통지 (해당 시)
5. 보안 절차 기록 및 업데이트

## 배포 워크플로우

### 배포 전 체크리스트
- [ ] 모든 테스트 통과
- [ ] 커버리지 >80%
- [ ] 린팅 에러 없음
- [ ] 모바일 테스트 완료
- [ ] 환경 변수 설정됨
- [ ] 데이터베이스 마이그레이션 준비됨
- [ ] 백업 생성됨

### 배포 단계
1. 기능 브랜치를 main에 병합
2. 버전을 태그하여 릴리스
3. 배포 서비스로 푸시
4. 데이터베이스 마이그레이션 실행
5. 배포 검증
6. 핵심 경로 테스트
7. 에러 모니터링

### 배포 후
1. 분석 데이터 모니터링
2. 에러 로그 확인
3. 사용자 피드백 수집
4. 다음 반복 계획
