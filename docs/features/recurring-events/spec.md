# 파트너 이벤트 반복 생성 (Recurring Events) 스펙

## 개요

파트너가 정기적으로 운영하는 파티(매주 금요일 와인파티, 격주 토요일 독서모임 등)에 대해 이벤트를 매번 수동으로 생성하는 비효율을 해소한다. 반복 규칙(recurrence rule)을 설정하면 시스템이 **최대 1개월 앞까지** 이벤트를 자동 생성한다.

**출처 이슈**: #1002

### 현재 상태 (문제)

| 소스 | 현재 동작 | 문제 |
|------|----------|------|
| **이벤트 생성 UI** (`EventCreatePage`) | 시작/종료 시간만 입력, 1회 생성 | 매주 동일 파티 운영 시 매번 수동 생성 |
| **데이터 모델** (`events` 테이블) | 개별 이벤트만 존재, 시리즈 개념 없음 | 반복 패턴 관리 불가 |
| **파티↔이벤트 관계** | Party(템플릿) → Event(회차) 1:N | 구조적으로 반복에 적합하나 자동화 없음 |

### 핵심 원칙

1. **템플릿 상속**: 파티(Party)가 이미 entry_groups, tickets, verifications의 템플릿 역할을 하므로, 반복 생성 시 파티 템플릿을 자동 복제
2. **개별 자율성**: 자동 생성된 이벤트도 개별 수정/취소 가능 (시리즈에서 분리)
3. **제한된 미래**: 최대 1개월 앞까지만 생성하여 데이터 폭증 방지
4. **점진적 복잡도**: V1은 단순한 반복 패턴만 지원, 고급 기능은 후속 버전

### 참고 앱

| 앱 | 반복 이벤트 접근 | 밍글릿 적용 포인트 |
|----|-----------------|-------------------|
| **Eventbrite** | 이벤트 생성 Date&Time에서 "Recurring event" 선택. 날짜+타임슬롯 2단계 계층. 슬롯별 가격 커스텀 가능 | 미국/캐나다 한정 기능. 슬롯별 커스텀은 V2 검토 |
| **Meetup** | Optional Settings에서 반복 주기 선택 (매주/격주/매월). 수정 시 "이 이벤트만" vs "시리즈 전체" 2-way | 2-way 편집 채택 (V1에서는 "이 이벤트만" 중심) |
| **Luma** | Event Series + Clone Event 병행. 커뮤니티 캘린더로 시리즈 구독 | 클론은 현행 수동 생성과 차이 없음. 시리즈 자동화가 핵심 |
| **Google Calendar** | 3-way 편집 (이것만/이후 모두/전체). RFC 5545 RRULE 기반 | 3-way 중 "이후 모든 이벤트"는 V2에서 검토. RRULE 참조 |

### 유저 시뮬레이션

**페르소나 1 — 매주 와인파티를 운영하는 바 오너 (35세, 남성)**
- 매주 금요일 19:00~22:00 와인파티를 운영. 현재 매주 수요일에 다음 주 이벤트를 수동 생성
- Pain: "매번 같은 내용인데 일일이 만들어야 해서 까먹을 때가 있다" → 반복 설정으로 자동 생성
- 기대: 한 번 설정하면 4주치가 미리 생성되어 있고, 특정 주만 취소/수정 가능
- 엣지 케이스: 연말 2주간 쉬는 경우 → "일시정지" 또는 개별 취소로 대응

**페르소나 2 — 격주 독서모임을 기획하는 북카페 대표 (42세, 여성)**
- 격주 토요일 14:00~16:00 독서모임. 매회 책이 다르므로 제목/설명은 회차별로 달라야 함
- Pain: "반복이라도 매번 내용이 다른데, 자동 생성되면 수정이 번거롭지 않을까?"
- 기대: 자동 생성 후 개별 이벤트의 제목/설명만 편집 가능. 시간/장소/티켓은 그대로 유지
- 엣지 케이스: 다음 달부터 시간을 15:00로 변경 → 반복 규칙 자체를 수정 (미래 미생성분에 반영)

**페르소나 3 — 매월 1회 대형 클럽파티를 여는 프로모터 (29세, 남성)**
- 매월 마지막 토요일 22:00~04:00 클럽파티. 매회 게스트 DJ와 가격이 다름
- Pain: "반복 생성은 편한데, 티켓 가격이 매번 달라야 한다"
- 기대: 자동 생성된 이벤트에서 티켓 가격만 개별 수정 가능
- 엣지 케이스: 특별 이벤트로 정원을 2배로 늘리고 싶음 → 개별 이벤트에서 max_participants 수정

## PM 결정 사항

이슈 #1002에서 요청한 5가지 PM 확정 항목에 대한 결정.

### 1. 반복 규칙 UI/UX 설계

**결정**: 이벤트 생성 Operation 탭의 "일정 설정" 섹션 아래에 "반복 설정" 섹션을 추가한다.

- 기본값: 반복 안 함 (기존 1회 생성과 동일)
- 반복 ON 시: 주기 선택 → 요일 선택 (주간 반복 시) → 종료 조건 설정
- 미리보기: 생성될 이벤트 날짜 목록을 하단에 표시

**근거**: Meetup의 "Optional Settings" 패턴 참조. 기존 플로우를 깨지 않으면서 선택적으로 확장.

### 2. 1개월 제한의 근거

**결정**: 유지 (최대 1개월 = 약 4~5회분).

| 대안 | 장점 | 단점 | 채택 |
|------|------|------|------|
| 1개월 | 데이터 폭증 방지, 관리 부담 적음 | 장기 예약 불가 | **V1 채택** |
| 3개월 | 분기 단위 계획 가능 | 미사용 이벤트 누적, 크론잡 부하 | V2 검토 |
| 무제한 | 최대 유연성 | DB 폭증, 취소/수정 관리 복잡 | 미채택 |

**근거**: 밍글릿의 이벤트는 소셜 매칭 특성상 1개월 이상 미리 예약하는 유저가 드물다. Eventbrite도 반복 이벤트의 공개 범위를 제한하는 옵션을 제공한다.

### 3. 티켓/가격 — 매회 동일 vs. 회차별 커스텀

**결정**: **V1은 파티 템플릿에서 동일 복제**, 생성 후 개별 이벤트에서 수정 가능.

- 자동 생성 시: `ticket_templates` → `tickets` 복제 (현행 단일 이벤트 생성과 동일 로직)
- 생성 후: 개별 이벤트의 이벤트 편집 화면에서 티켓 가격/수량 수정 가능
- 반복 규칙에 "기본 가격 오버라이드" 같은 고급 기능은 넣지 않음

**근거**: 페르소나 3(클럽 프로모터)의 니즈는 인정하지만, V1에서 복잡도를 추가하기보다 "생성 후 개별 편집"으로 충분히 대응 가능. Eventbrite도 이 방식이 기본이고, 슬롯별 커스텀은 신규 경험에서만 지원.

### 4. 파티 템플릿 복제 범위

**결정**: 현행 단일 이벤트 생성과 동일한 범위를 복제한다.

| 파티 템플릿 항목 | 복제 여부 | 비고 |
|-----------------|----------|------|
| `entry_group_templates` → `entry_groups` | O | 입장 조건 |
| `ticket_templates` → `tickets` | O | 티켓 유형/가격 |
| `title`, `description` | O | 파티명/설명 상속 |
| `image_urls` | O | 대표 이미지 |
| `location_id` | O | 장소 |
| `max_participants` | O | 정원 |
| `contact_options` | O | 연락처 |
| `visibility` | O | 공개 여부 |

**근거**: Party → Event 생성 시 이미 구현된 복제 로직을 재사용. 새로운 복제 범위를 추가하지 않아 구현 리스크 최소화.

### 5. 반복 이벤트 수정 시 선택지

**결정**: V1은 **"이 이벤트만" 단일 모드**. "이후 모든 이벤트" / "모든 이벤트" 수정은 V2에서 검토.

| 수정 대상 | V1 | V2 검토 |
|----------|-----|---------|
| 이 이벤트만 수정 | O | O |
| 이후 모든 이벤트 수정 | X | O |
| 모든 이벤트 수정 | X | O |
| 이 이벤트만 취소 | O | O |
| 시리즈 전체 취소 | X | O |

**근거**: Meetup도 "이 이벤트만" 수정 시 시리즈에서 분리(독립 이벤트 전환)하는 단순한 모델을 사용한다. 3-way 편집(Google Calendar 스타일)은 DB 설계와 UX 양면에서 복잡도가 크므로, MVP에서는 과투자.

### 3. 반복 관리 액션

| 액션 | 동작 | 비고 |
|------|------|------|
| **일시정지** | `recurrence_rules.status` → `paused`. 크론잡이 새 이벤트를 생성하지 않음. 기존 생성분 유지 | 재개 시 `active`로 복원 |
| **규칙 수정** | 반복 주기/요일/종료 조건 변경. **미래 미생성 이벤트에만 반영** | 이미 생성된 이벤트는 변경 없음 |
| **반복 해제** | `recurrence_rules.status` → `cancelled`. 기존 생성 이벤트는 유지 | 되돌리기 불가 — 확인 다이얼로그 |
| **이번 회차 건너뛰기** | 특정 이벤트를 `cancelled`로 변경 | 개별 이벤트 단위 조작 |
| **개별 이벤트 수정** | 제목/설명/가격/정원 등 개별 편집 | 시리즈와 무관하게 독립 변경 |

## 데이터 소스

### 신규 테이블: `recurrence_rules`

| 컬럼 | 타입 | 설명 |
|------|------|------|
| `id` | uuid PK | 규칙 ID |
| `party_id` | uuid FK → parties | 대상 파티 |
| `pattern` | text | `'weekly'` \| `'biweekly'` \| `'monthly'` |
| `days_of_week` | int[] | 반복 요일 (1=월~7=일). weekly/biweekly에서 사용 |
| `month_day` | int | 매월 N일. monthly에서 사용 (null이면 "매월 N번째 X요일" 패턴) |
| `start_time` | time | 이벤트 시작 시각 (시간 부분만) |
| `end_time` | time | 이벤트 종료 시각 |
| `end_date` | date | 반복 종료일 (null = 무기한) |
| `status` | text | `'active'` \| `'paused'` \| `'cancelled'` |
| `last_generated_date` | date | 마지막으로 이벤트를 생성한 날짜 (크론잡 추적) |
| `created_at` | timestamptz | 생성일 |
| `updated_at` | timestamptz | 수정일 |

### `events` 테이블 확장

| 컬럼 추가 | 타입 | 설명 |
|----------|------|------|
| `recurrence_rule_id` | uuid FK → recurrence_rules | 반복 규칙 참조 (null = 단일 이벤트) |
| `is_recurrence_exception` | boolean | 시리즈에서 개별 수정된 이벤트 여부 |

### API / Edge Function

| 엔드포인트 | 메서드 | 설명 |
|-----------|--------|------|
| `POST /parties/:id/recurrence-rules` | 생성 | 반복 규칙 생성 + 즉시 1개월분 이벤트 배치 생성 |
| `PATCH /recurrence-rules/:id` | 수정 | 규칙 수정 (미래 미생성분에만 반영) |
| `POST /recurrence-rules/:id/pause` | 일시정지 | status → paused |
| `POST /recurrence-rules/:id/resume` | 재개 | status → active + 부족분 즉시 생성 |
| `DELETE /recurrence-rules/:id` | 해제 | status → cancelled |

### 크론잡 (Edge Function + pg_cron)

- **실행 주기**: 매일 UTC 00:00 (KST 09:00)
- **로직**: `recurrence_rules` WHERE `status = 'active'`인 규칙에 대해, `last_generated_date`부터 1개월 윈도우 내 미생성 이벤트를 배치 생성
- **배치 생성 시**: `parties` 테이블에서 template 데이터 복제 (entry_groups, tickets 포함)
