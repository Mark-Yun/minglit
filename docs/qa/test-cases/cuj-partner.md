# 파트너 앱 (app_partner) CUJ 테스트 시나리오

> CUJ = Critical User Journey
>
> 목적: 핵심 파트너 플로우가 end-to-end로 정상 동작하는지 검증.
> 파트너 앱은 이벤트 운영 도구이므로 "생성 → 관리 → 정산"이 핵심 경로.

---

## 우선순위 정의

| 등급 | 의미 | 기준 |
|------|------|------|
| **P0** | 핵심 비즈니스 경로 | 이벤트 운영의 기반 — 실패 시 파트너 서비스 불가 |
| **P1** | 필수 파트너 경험 | 가입/인증/심사 — 실패 시 파트너 온보딩 불가 |
| **P2** | 보조 관리 기능 | 멤버 관리/알림 — 실패 시 불편하지만 운영 가능 |

---

## CUJ-P01: 파트너 가입 → 파티 생성 → 이벤트 생성 → 티켓 설정 [P0]

> 파트너가 서비스에 등록하고 첫 이벤트를 개설하는 전체 플로우.
> 파트너 수 = 이벤트 수 = 유저 유입의 기반.

### 사전 조건
- 소셜 로그인 가능한 계정
- 사업자등록증 등 서류 준비

### 시나리오 스텝

| Step | 화면 | 액션 | 기대 결과 | 실패 시 |
|------|------|------|-----------|---------|
| 1 | 로그인 (`/login`) | 소셜 로그인 | 로그인 성공 → 파트너 미등록 → `/welcome` | OAuth 실패 → 에러 |
| 2 | 웰컴 (`/welcome`) | "시작하기" 탭 | `/apply`로 이동 | - |
| 3 | 신청 위저드 (`/apply`) Step 1 | 기본정보 입력 (상호명, 카테고리) | 다음 스텝 | 필수 필드 누락 → 유효성 검사 |
| 4 | 신청 위저드 Step 2 | 사업자 정보 입력 | 다음 스텝 | 사업자번호 유효성 검사 실패 |
| 5 | 신청 위저드 Step 3 | 연락처 + 정산 계좌 입력 | 다음 스텝 | - |
| 6 | 신청 위저드 Step 4 | 서류 업로드 | 다음 스텝 | 파일 크기 초과 → 에러 |
| 7 | 신청 위저드 Step 5 | 검토 + 제출 | 신청 완료 → `/apply/status` | 서버 오류 → 재시도 |
| 8 | 신청 상태 (`/apply/status`) | 대기 | 심사 상태 표시 ("심사 중") | - |
| 9 | — (관리자 승인 후) | 앱 재진입 | `/` 대시보드로 이동 | - |
| 10 | 더보기 → 파티 목록 | "파티 만들기" 탭 | `/more/parties/create`로 이동 | - |
| 11 | 파티 생성 위저드 Step 1 | 기본정보 (파티명, 설명, 이미지) | 다음 스텝 | 필수 필드 누락 |
| 12 | 파티 생성 위저드 Step 2 | 장소 (주소 검색 + 선택) | 다음 스텝 | 주소 검색 API 오류 |
| 13 | 파티 생성 위저드 Step 3 | 정원 + 연락처 | 다음 스텝 | - |
| 14 | 파티 생성 위저드 Step 4 | 입장규칙 | 다음 스텝 | - |
| 15 | 파티 생성 위저드 Step 5 | 티켓 설정 | 다음 스텝 | - |
| 16 | 파티 생성 위저드 Step 6 | 검토 + 제출 | 파티 생성 완료 → 파티 상세 | 서버 오류 |
| 17 | 파티 상세 | "이벤트 만들기" 탭 | `/more/parties/:id/events/create`로 이동 | - |
| 18 | 이벤트 생성 | 날짜/시간/설명 입력 → 생성 | 이벤트 생성 완료 → 이벤트 상세 | 과거 날짜 → 유효성 검사 |
| 19 | 이벤트 상세 | "티켓 추가" 탭 | `.../tickets/create`로 이동 | - |
| 20 | 티켓 생성 | 티켓명, 가격, 수량 입력 → 생성 | 티켓 생성 완료 | 가격 음수 → 유효성 검사 |

### 검증 포인트
- [ ] 파트너 신청 → 승인 후 대시보드 접근 가능
- [ ] 파티 생성 시 DB에 party 레코드 생성
- [ ] 이벤트 생성 시 DB에 event 레코드 + party 연결
- [ ] 티켓 생성 후 유저 앱에서 해당 이벤트 + 티켓 표시
- [ ] 파티 생성 위저드 중간 이탈 시 작성 내용 유실 경고

### 변형 시나리오

| 변형 | 차이점 | 추가 검증 |
|------|--------|-----------|
| P01-V1: 심사 보완 요청 | Step 8에서 `needsCorrection` | 보완 요청 내용 표시 + 수정 후 재제출 |
| P01-V2: 무료 이벤트 | Step 20에서 가격 0원 | 결제 없이 신청 가능 여부 |
| P01-V3: 위저드 중간 이탈 + 재진입 | Step 11~16 중간에 앱 종료 | 임시 저장/복구 여부 |

## CUJ-P02: 신청 관리 → 심사 (승인/거절) [P0]

> 유저 신청을 관리하는 핵심 운영 플로우.

### 사전 조건
- PARTNER 상태
- 유저가 신청한 이벤트 1건 이상 (status: pending)

### 시나리오 스텝

| Step | 화면 | 액션 | 기대 결과 | 실패 시 |
|------|------|------|-----------|---------|
| 1 | 대시보드 (`/`) | 신청관리 탭 탭 | `/applications`로 이동 | - |
| 2 | 신청 관리 (`/applications`) | 이벤트 필터 선택 | 해당 이벤트의 신청 목록 표시 | 신청 0건 → 빈 상태 |
| 3 | 신청 관리 | 신청 항목 탭 | `/applications/:id` 상세로 이동 | - |
| 4 | 신청 상세 (`/applications/:id`) | 유저 정보/인증 상태 확인 | 유저 프로필 + 인증 정보 표시 | - |
| 5a | 신청 상세 | "승인" 버튼 탭 | 승인 확인 → 상태 `approved`로 변경 | 이미 처리됨 → 에러 |
| 5b | 신청 상세 | "거절" 버튼 탭 | 거절 사유 입력 → 상태 `rejected`로 변경 | - |
| 6 | 신청 관리 | 목록 복귀 | 처리된 신청의 상태 반영 | - |

### 검증 포인트
- [ ] 승인 후 유저에게 승인 알림 전송
- [ ] 거절 후 유저에게 거절 알림 + 사유 전달
- [ ] 동시 처리 방지 (다른 멤버가 이미 처리한 경우)
- [ ] 신청 상태 변경이 DB에 반영

### 변형 시나리오

| 변형 | 차이점 | 추가 검증 |
|------|--------|-----------|
| P02-V1: 정원 초과 시 승인 | 이벤트 정원이 다 찬 상태 | 정원 초과 경고 또는 차단 |
| P02-V2: 일괄 승인 | 여러 신청 동시 승인 | 배치 처리 정상 동작 |

## CUJ-P03: 이벤트 운영 → 체크인 관리 [P0]

> 이벤트 당일 현장 운영 플로우.

### 사전 조건
- PARTNER 상태
- 당일 이벤트 존재 (승인된 신청자 있음)

### 시나리오 스텝

| Step | 화면 | 액션 | 기대 결과 | 실패 시 |
|------|------|------|-----------|---------|
| 1 | 대시보드 (`/`) | 체크인 탭 탭 | `/checkin`으로 이동 | - |
| 2 | 체크인 (`/checkin`) | QR 스캐너 활성화 | 카메라 권한 요청 → QR 스캐너 표시 | 권한 거부 → 수동 입력 안내 |
| 3 | 체크인 | 유저 QR 코드 스캔 | 체크인 처리 → 성공 피드백 | 유효하지 않은 QR → "유효하지 않은 코드" |
| 4 | 체크인 | 스캔 결과 확인 | 유저명 + 티켓 정보 표시 | - |

### 검증 포인트
- [ ] QR 스캔 후 유저의 attendance 상태가 `checked_in`으로 변경
- [ ] 이미 체크인된 유저를 다시 스캔 시 "이미 체크인됨" 안내
- [ ] 다른 이벤트의 QR 코드 스캔 시 에러 처리
- [ ] 승인되지 않은 유저의 QR 스캔 시 거부

### 변형 시나리오

| 변형 | 차이점 | 추가 검증 |
|------|--------|-----------|
| P03-V1: 카메라 권한 거부 | 카메라 접근 불가 | 수동 체크인 대안 제공 |
| P03-V2: 오프라인 체크인 | 네트워크 불안정 | 오프라인 큐잉 + 복구 |

## CUJ-P04: 정산 확인 → 계좌 관리 [P0]

> 파트너의 수익 확인 + 정산 계좌 관리.

### 사전 조건
- PARTNER 상태
- 정산 가능한 이벤트 (완료된 이벤트 + 결제 건)

### 시나리오 스텝

| Step | 화면 | 액션 | 기대 결과 | 실패 시 |
|------|------|------|-----------|---------|
| 1 | 대시보드 (`/`) | 정산 탭 탭 | `/settlement`로 이동 | - |
| 2 | 정산 (`/settlement`) | 정산 목록 확인 | 이벤트별 정산 내역 표시 | 정산 없음 → 빈 상태 |
| 3 | 정산 | 정산 항목 탭 | `/settlement/:id` 상세로 이동 | - |
| 4 | 정산 상세 (`/settlement/:id`) | 상세 내역 확인 | 매출, 수수료, 정산금액 표시 | - |
| 5 | 정산 | "계좌 관리" 탭 | `/settlement/bank-account`로 이동 | - |
| 6 | 계좌 관리 (`/settlement/bank-account`) | 계좌 등록/변경 | 은행 선택 → 계좌번호 입력 → 저장 | 유효성 검사 실패 |

### 검증 포인트
- [ ] 정산 금액 = 총 매출 - 수수료가 정확한가
- [ ] 정산 상태 (대기/완료/오류) 정확히 표시
- [ ] 계좌 변경 후 다음 정산에 새 계좌 적용
- [ ] 정산 상세에서 개별 결제 건 확인 가능

## CUJ-P05: 파티 관리 → 이벤트/티켓 편집 [P1]

> 생성된 파티와 이벤트를 관리하는 플로우.

### 사전 조건
- PARTNER 상태
- 파티 + 이벤트 + 티켓 생성 완료

### 시나리오 스텝

| Step | 화면 | 액션 | 기대 결과 | 실패 시 |
|------|------|------|-----------|---------|
| 1 | 더보기 (`/more`) | "파티 관리" 탭 | `/more/parties`로 이동 | - |
| 2 | 파티 목록 (`/more/parties`) | 파티 카드 탭 | `/more/parties/:id` 상세로 이동 | - |
| 3 | 파티 상세 | 탭 전환 (정보/운영/이벤트/규칙) | 각 탭 내용 표시 | - |
| 4 | 파티 상세 | "편집" 버튼 탭 | `/more/parties/:id/edit` → 편집 위저드 | - |
| 5 | 파티 편집 | 정보 수정 → 저장 | 변경 사항 저장 → 상세 복귀 | 서버 오류 |
| 6 | 파티 상세 → 이벤트 탭 | 이벤트 카드 탭 | 이벤트 상세로 이동 | - |
| 7 | 이벤트 상세 | 티켓 항목 탭 | `.../tickets/:id/edit`로 이동 | - |
| 8 | 티켓 편집 | 가격/수량 변경 → 저장 | 변경 저장 | 이미 판매된 티켓 가격 변경 → 경고 |

### 검증 포인트
- [ ] 편집 후 유저 앱에서 변경된 정보 반영
- [ ] 이벤트 상태별 편집 가능 범위 (scheduled → 전체 편집, in_progress → 제한적)
- [ ] 티켓 수량 감소 시 이미 판매된 수량보다 작으면 차단

### 변형 시나리오

| 변형 | 차이점 | 추가 검증 |
|------|--------|-----------|
| P05-V1: 진행 중 이벤트 편집 | 이벤트 status: in_progress | 날짜 변경 불가 등 제한 |
| P05-V2: 파티 티켓 템플릿 편집 | 파티 레벨 티켓 수정 | 기존 이벤트 티켓에 영향 없음 |

## CUJ-P06: 멤버 관리 → 권한 변경 [P2]

> 파트너 조직의 멤버를 관리하는 플로우.

### 사전 조건
- PARTNER 상태 (owner 또는 admin 권한)
- 멤버 1명 이상 존재

### 시나리오 스텝

| Step | 화면 | 액션 | 기대 결과 | 실패 시 |
|------|------|------|-----------|---------|
| 1 | 더보기 (`/more`) | "멤버 관리" 탭 | `/more/partners/:id/members`로 이동 | - |
| 2 | 멤버 목록 | 멤버 항목 탭 | `.../members/:userId/permission`으로 이동 | - |
| 3 | 멤버 권한 | 권한 변경 (viewer → editor 등) | 저장 → 목록 갱신 | 자기 자신 → 변경 불가 |
| 4 | 멤버 권한 | "멤버 제거" 탭 | 확인 다이얼로그 → 제거 처리 | 마지막 admin → 차단 |

### 검증 포인트
- [ ] 권한 변경 후 해당 멤버의 접근 범위 즉시 반영
- [ ] owner는 admin 권한 변경 가능, admin은 editor/viewer만 가능
- [ ] 마지막 admin/owner 제거 방지
- [ ] 제거된 멤버가 앱 재접근 시 `/welcome`으로 리다이렉트

## CUJ-P07: 인증(자격 검증) 관리 [P2]

> 유저 자격 검증을 위한 인증 설정 플로우.

### 사전 조건
- PARTNER 상태

### 시나리오 스텝

| Step | 화면 | 액션 | 기대 결과 | 실패 시 |
