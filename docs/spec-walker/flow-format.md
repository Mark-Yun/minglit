# Flow 파일 작성 가이드

피쳐 오너가 `flows/<name>.md` 에 자기가 관심 있는 재현 경로를 markdown 으로 작성한다. 자유 형식이지만 워커가 안정적으로 읽으려면 아래 구조를 권장한다.

## 파일 위치 및 이름

- 위치: `docs/spec-walker/flows/<name>.md`
- 이름: kebab-case, 어떤 시나리오인지 알 수 있게 (예: `user-event-application.md`, `partner-onboarding-success.md`)
- 한 파일에 하나의 경로만 (분기는 다른 파일로 분리)

## 권장 섹션

### 1. 개요

한두 줄. 이 경로가 무엇을 재현하는지.

### 2. Setup

워커가 실행 전 만족해야 할 상태 (시드 사용자, 권한, 환경 등). 워커가 자동 처리 불가능한 사전 조건은 명시한다.

### 3. Steps

번호 매긴 단계 목록. 각 단계는 워커가 디바이스에서 수행할 단일 액션.

권장 형식:

```
1. **<액션 한 줄>**
   - 화면: <expected screen / Route>
   - 트리거: <tap / scroll / input 등 구체적 동작>
   - 스크린샷: <yes/no>
   - 메모: <워커가 알아야 할 추가 정보, optional>
```

### 4. (선택) 검증 포인트

피쳐 오너가 "이 단계의 스크린샷에서 보고 싶은 것" 을 명시. 워커는 비교 안 하지만, 사람이 results/ 를 볼 때 가이드가 된다.

## 예시

`flows/_example.md` 참고.

## 워커가 못 읽으면

워커가 LLM 기반이라 자연어 markdown 을 읽지만, 다음은 피해서 작성한다.

- 과도하게 추상적인 트리거 ("적절한 곳을 누른다" 같은)
- 외부 의존성이 있는 단계 (이메일 OAuth 콜백 등)
- 한 단계에 여러 액션 묶기

워커가 3회 실행에서 같은 단계에 실패하면 해당 flow 는 `results/<name>/walk-log.md` 에 `STALE` 표시를 남긴다. 피쳐 오너가 flow 파일을 보정한다.
