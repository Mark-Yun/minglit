- 코드가 최신이고 약관이 미업데이트인 건지?
- DB Vault 정책이 동적으로 변경 가능한 설계인 건지?

### 2. 전자상거래법 준수 분석

#### [Critical] 전자상거래법 제17조 — 7일 청약철회 gap

**법적 근거**: 전자상거래 등에서의 소비자보호에 관한 법률 제17조 제1항
> 소비자는 계약내용에 관한 서면을 교부받은 날부터 **7일 이내** 청약철회 가능

**제17조 제2항 제5호 예외**: 용역 제공이 **개시된 경우** 청약철회 제한 가능
- 밍릿의 "모임 참여"는 용역에 해당
- 용역 개시 시점 = **모임 당일** (실제 모임 시작 시)
- 따라서 모임 시작 전이라면 용역 미개시 → **7일 청약철회 적용**

**현재 코드의 문제 시나리오**:

| 시나리오 | 결제 후 경과 | 이벤트까지 | 코드 결과 | 법적 요건 | 위반? |
|----------|-------------|-----------|----------|----------|------|
| A | 1일 | 6일 후 | ❌ 환불 불가 (2h 초과 + 7일 미만) | ✅ 7일 이내 환불 가능 | **⚠️ 위반** |
| B | 3일 | 5일 후 | ❌ 환불 불가 | ✅ 7일 이내 환불 가능 | **⚠️ 위반** |
| C | 6일 | 2일 후 | ❌ 환불 불가 | ✅ 7일 이내 환불 가능 | **⚠️ 위반** |
| D | 1시간 | 3일 후 | ✅ grace period | ✅ | OK |
| E | 1일 | 10일 후 | ✅ cutoff | ✅ | OK |

**핵심**: 결제 후 2시간~7일 사이 AND 이벤트 7일 미만인 구간에서 **전자상거래법상 보장된 청약철회권이 차단**됨.

**위험**: 공정거래위원회 시정조치, 과태료, 소비자 분쟁 시 패소 가능성

#### [Critical] 약관-코드 불일치 자체의 법적 리스크

**법적 근거**: 약관의 규제에 관한 법률 제5조 (약관의 명시·설명의무)
- 약관에 "3일 전 전액/2~1일 전 50%"로 고지하면서 코드에서는 "2시간/7일 binary"로 동작
- 소비자에게 고지한 약관보다 **불리한 조건**을 코드로 적용 → 무효 가능성
- 소비자 분쟁 시 약관 내용이 적용될 가능성 높음

#### [Medium] 전자상거래법 제17조 제6항 — 청약철회 제한 고지 의무

용역의 특성상 청약철회가 제한되는 경우, **사전 고지 + 시용 상품 제공 등 조치** 의무:
- 현재 약관은 모임 특수성(사전 준비)을 언급하나, 코드(2시간/7일) 기준은 약관에 기재되지 않음
- 소비자가 결제 시 **실제 적용되는 환불 정책**을 인지할 수 없는 상태

### 3. 권장 조치

#### 옵션 B 수정안 (코드 기준 유지 + 법률 보완)

Mark가 코드 기준을 의도했으므로, 코드를 유지하되 **전자상거래법 7일 청약철회를 추가 조건으로 보장**:

```
환불 가능 조건 (OR):
1. 결제 후 2시간 이내 (grace period) → 전액 환불
2. 이벤트 7일 전 이상 → 전액 환불
3. [추가 필요] 결제 후 7일 이내 AND 용역(모임) 미개시 → 전액 환불
```

이렇게 하면:
- 장소공유 플랫폼 참고한 binary 정책 유지
- 전자상거래법 7일 청약철회 준수
- 시나리오 A~C 모두 해결

#### 약관 수정 (필수)

코드 기준 + 법률 보완한 최종 정책으로 약관 업데이트:

```
제1조 (참여자의 취소 및 환불)
- 결제 후 2시간 이내: 전액 환불
- 모임 시작 7일 전까지: 전액 환불
- 결제일로부터 7일 이내(모임 미개시): 전액 환불 (전자상거래법 제17조)
- 상기 조건에 해당하지 않는 경우: 환불 불가
```

## 분석 결과 업데이트 (2026-04-04)

이슈 보고 시점보다 상황이 복잡합니다. **3곳 모두 다른 정책을 갖고 있습니다.**

### 현재 상태

| 소스 | 환불 기준 | 비고 |
|---|---|---|
| **약관** (`landing_user/terms/page.tsx:72-74`) | 3일 전 100% / 2~1일 전 50% / 당일 0% | 소비자 공개 문서 |
| **DB 정책** (`policies` seed, `refund` key) | 7일+ 100% / 3~7일 80% / 1~3일 50% / 당일 0% | 4단계 tier |
| **코드** (`refund_utils.ts` + `user-cancel-order`) | grace period 2시간 OR cutoff 7일 → 전액/불가 | **tier 미사용, 부분환불 없음** |

### 핵심 문제

1. **DB tier 정책이 코드에서 무시됨** — `verifyRefundEligibility()`는 `grace_period_hours`와 `cutoff_days`만 사용하고, DB의 `tiers[]` 배열을 읽지 않음
2. **부분환불 로직 자체가 없음** — `executeRefund()`에 `amount: paymentAmount` (전액) 고정
3. **약관 ≠ DB ≠ 코드** — 3곳 다 다른 정책

### 방향 결정

**플랫폼 환불과 파트너 환불을 분리한다.**

| 구분 | 주체 | 정책 | 처리 방식 |
|---|---|---|---|
| **플랫폼 자동 환불** | Minglit | 7일 전 + 결제 후 3시간 이내 → 전액 환불 | 코드에서 DB 정책 읽어서 자동 처리 |
| **파트너 환불** | 파트너 | 전자상거래법 제17조/18조 기준 (3일/2일/1일) | 플랫폼은 게이팅만, 유저가 파트너에게 연락하여 환불 진행 |
