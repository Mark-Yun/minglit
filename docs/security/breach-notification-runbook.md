# 개인정보 유출 통지 운영 Runbook

> **문서 버전**: v1.0
> **최종 수정**: 2026-04-09
> **관련 이슈**: #1181
> **상위 문서**: [breach-response-process.md](./breach-response-process.md)
> **법적 근거**: 개인정보보호법 제34조 (개정, 2026.09.11 시행)

---

## 1. 개요

이 runbook은 개인정보 유출 사고 발생 시 **발견(H+0)부터 통지 완료(H+72)까지**의 실무 절차를 시간대별로 정리한다. [breach-response-process.md](./breach-response-process.md)의 대응 프로세스를 실행 가능한 체크리스트로 구체화한 문서이다.

### 핵심 규정

- **72시간 기한**: 유출등을 **알게 된 시점**부터 72시간 이내에 개인정보보호위원회 신고 + 정보주체 통지
- **가능성 통지**: 유출 가능성 인지 시 확정 전에도 지체 없이 정보주체에게 통지 (제34조 제5항, 신설)
- **CI/DI 보유**: 밍릿은 고유식별정보(CI/DI)를 보유하므로 **1건이라도 유출되면 보호위 신고 의무 발생**

## 2. 시간별 체크리스트

### H+0 ~ H+1: 즉시 조치

**목표**: 추가 유출 차단, 증거 보전, 대응 시작

- [ ] 유출/이상 징후 확인 (Axiom 로그, Sentry 알림, 외부 제보 등)
- [ ] **T=0 시점 기록**: `YYYY-MM-DD HH:MM KST` — 이 시점이 72시간 기산점
- [ ] Mark(대응팀장)에게 즉시 보고 (Slack DM 또는 전화)
- [ ] 증거 보전:
  - [ ] Supabase Dashboard 로그 스크린샷/내보내기
  - [ ] Axiom에서 해당 시간대 Edge Function 로그 저장
  - [ ] Sentry 이벤트 보전 (삭제 방지 설정)
  - [ ] PostgreSQL 로그 확인 (Supabase Dashboard → Database → Logs)
- [ ] 긴급 봉쇄:
  - [ ] 유출 경로 식별 및 차단 (RLS 긴급 보강, 의심 Edge Function 비활성화)
  - [ ] service_role_key 노출 시: Dashboard → Settings → API → Regenerate
  - [ ] 의심 세션 강제 종료: `DELETE FROM auth.sessions WHERE user_id = '...'`
  - [ ] 필요 시 Supabase Network Restrictions로 IP 차단

### H+1 ~ H+4: 초기 평가

**목표**: 심각도 확정, 영향 범위 추정

- [ ] 심각도 등급 판정 (breach-response-process.md §3 참조)
- [ ] 유출된 데이터 항목 초기 목록:
  - [ ] 고유식별정보 (CI/DI) 포함 여부
  - [ ] 개인정보 (성명, 생년월일, 성별, 전화번호) 포함 여부
  - [ ] 사업자 정보 (계좌, 연락처) 포함 여부
  - [ ] 인증 서류 (verification_submissions) 포함 여부
- [ ] 영향받은 사용자 수 초기 추정
- [ ] 유출 경로 초기 파악 (RLS 미적용? API 취약점? 키 노출? 내부자?)
- [ ] `sensitive_access_log` 테이블 확인 (배포된 경우):
  ```sql
  SELECT * FROM public.sensitive_access_log
  WHERE occurred_at >= '유출 추정 시작 시점'
  ORDER BY occurred_at DESC;
  ```

### H+4 ~ H+12: 원인 분석 및 범위 확정

**목표**: 정확한 유출 범위와 원인 확정

- [ ] 유출 타임라인 재구성 (최초 유출 시점 → 인지 시점 → 차단 시점)
- [ ] Axiom 쿼리로 Edge Function 호출 패턴 분석
- [ ] 영향받은 레코드 정확한 수 산정:
  ```sql
  -- 예시: 특정 기간 내 비정상 접근된 user_profiles 수
  SELECT COUNT(DISTINCT row_id) FROM public.sensitive_access_log
  WHERE table_name = 'user_profiles'
    AND occurred_at BETWEEN '시작' AND '종료'
    AND role_name != 'authenticated';
  ```
- [ ] 2차 피해 가능성 평가 (계정 탈취, 신분 도용, 금전 피해 등)
- [ ] 유출 범위 최종 확정 문서 작성

### H+12 ~ H+24: 가능성 통지 및 통지 준비

**목표**: 가능성 통지 발송, 정식 통지문 준비

- [ ] **[가능성 통지]** 유출 확정 전이라도 가능성 인지 시 정보주체에게 통지:
  - [ ] 통지 대상 사용자 목록 확정
  - [ ] 가능성 통지문 작성 (§4.1 템플릿 사용)
  - [ ] notification-worker + FCM으로 푸시 발송
- [ ] 정식 통지문 초안 작성:
  - [ ] 개인정보보호위원회 신고서 (§4.2 템플릿)
  - [ ] 사용자 통지문 (§4.3 템플릿)
- [ ] 통지 채널 결정:
  - [ ] 앱 푸시 (FCM via notification-worker) — **1순위**
  - [ ] 이메일 (auth.users.email)
  - [ ] SMS (본인인증 시 수집한 전화번호)
  - [ ] 홈페이지 게시 (1,000명 이상 시 필수)

### H+24 ~ H+48: 통지문 확정 및 테스트

**목표**: 통지문 최종 확정, 발송 준비 완료

- [ ] 통지문 최종 검토 (Mark 승인)
- [ ] 통지 발송 테스트 (dev 환경에서 테스트 사용자에게 발송)
- [ ] 1,000명 이상 유출 시:
  - [ ] 홈페이지 게시 페이지 준비 (landing_user, landing_partner)
  - [ ] 30일 이상 게시 일정 확인
- [ ] 개인정보보호위원회 신고서 최종 확정

### H+48 ~ H+72: 통지 실행

**목표**: 법적 기한 내 모든 통지 완료

- [ ] **개인정보보호위원회 신고**:
  - [ ] https://privacy.go.kr 접속 → 개인정보 유출 신고
  - [ ] 신고서 제출 및 접수번호 기록
  - [ ] 제출 증빙 스크린샷 보관
- [ ] **사용자 통지 발송**:
  - [ ] FCM 푸시 발송 (notification-worker PGMQ 큐 사용)
  - [ ] 이메일 발송 (해당 시)
  - [ ] 발송 완료 로그 확인 및 저장
- [ ] **1,000명 이상 시 추가 조치**:
  - [ ] 홈페이지 공지 게시
  - [ ] KISA(한국인터넷진흥원)에 서면 신고
- [ ] **통지 완료 기록**:
  - [ ] 통지 일시, 방법, 대상 수 기록
  - [ ] 모든 증빙 자료 보관 (3년 이상)

### H+72 이후: 후속 조치

- [ ] 근본 원인 수정 및 패치 배포
- [ ] 재발 방지 대책 수립
- [ ] 보호위 후속 보고 (요청 시)
- [ ] Post-Incident Review 실시 (2주 이내)
- [ ] 재발 방지 대책 GitHub Issue 생성

## 3. 의사결정 트리 (Escalation)

### 3.1 심각도별 에스컬레이션

```
유출 징후 감지
│
├─ 고유식별정보(CI/DI) 포함 or 100명+ 영향?
│   ├─ YES → S1: Mark 즉시 전화 보고 → 전체 대응 프로세스 가동
│   └─ NO
│       ├─ 개인정보(L2/L3) 포함?
│       │   ├─ YES → S2: Mark Slack 즉시 보고 → 4시간 내 대응 시작
│       │   └─ NO
│       │       ├─ 인증 데이터(L4) or 동의이력(L5)?
│       │       │   ├─ YES → S3: Mark Slack 보고 → 24시간 내 대응
│       │       │   └─ NO → S4: GitHub Issue 생성 → 72시간 내 대응
│       │       └─
│       └─
└─
```

## 5. 증거 보전 체크리스트

사고 발생 시 아래 증거를 즉시 수집하고 보전한다. **로그 삭제/덮어쓰기 절대 금지**.

### 5.1 수집 항목

| 출처 | 수집 항목 | 보관 방법 |
|------|-----------|-----------|
| **Axiom** | 해당 시간대 Edge Function 로그 전체 | Axiom 쿼리 결과 export (JSON) |
| **Sentry** | 관련 에러 이벤트, 트랜잭션 | Sentry 이벤트 permalink 저장 |
| **Supabase Dashboard** | Auth 로그, Database 로그 | 스크린샷 + CSV export |
| **PostgreSQL** | `sensitive_access_log` 해당 기간 전체 | `COPY TO` 또는 쿼리 결과 저장 |
| **PostgreSQL** | 관련 테이블의 현재 상태 | 쿼리 결과 저장 (마스킹 적용) |
| **GitHub** | 의심 커밋, 배포 이력 | permalink 저장 |
| **네트워크** | Supabase Network Restrictions 로그 | Dashboard 스크린샷 |

### 5.2 보관 규칙

- **보관 기간**: 최소 3년 (법적 소송 대비)
- **보관 위치**: 별도 보안 스토리지 (Supabase 프로젝트와 분리)
- **무결성**: 수집 시 SHA-256 해시 기록, 이후 변조 여부 검증 가능하도록 보관
- **접근 제한**: Mark(대응팀장)만 접근 가능

### 5.3 증거 수집 명령어

```bash
# Axiom: Edge Function 로그 내보내기 (CLI가 설정된 경우)
# 시간 범위를 유출 추정 시점 전후로 설정
axiom query "['minglit-edge-functions'] | where _time >= '2026-04-09T00:00:00Z'" -f json > evidence_axiom_$(date +%Y%m%d).json

# PostgreSQL: 감사 로그 내보내기 (Supabase SQL Editor에서)
COPY (
    SELECT * FROM public.sensitive_access_log
    WHERE occurred_at >= '유출 추정 시작 시점'
    ORDER BY occurred_at
) TO STDOUT WITH CSV HEADER;

# SHA-256 해시 생성 (수집한 파일마다)
shasum -a 256 evidence_*.json evidence_*.csv > evidence_checksums.sha256
```

## 6. Edge Case 처리

### 6.1 주말/공휴일에 유출 발견 시

- 72시간 기한은 주말/공휴일과 무관하게 적용된다
- Mark에게 즉시 전화 연락 (Slack 응답 지연 가능성)
- 보호위 온라인 신고 시스템(privacy.go.kr)은 24시간 접수 가능
- 긴급 봉쇄는 AI Worker가 자동 실행 가능 (RLS 보강, Edge Function 비활성화)

### 6.2 파트너 데이터 vs 사용자 데이터

| 구분 | 파트너 데이터 유출 | 사용자 데이터 유출 |
|------|-------------------|-------------------|
| 주요 테이블 | `partner_settlements`, `partners` | `user_profiles`, `verification_submissions` |
| 통지 대상 | 해당 파트너 담당자 (partner_member_permissions의 owner) | 해당 사용자 |
| 통지 방법 | 개별 연락 (이메일/전화) 우선 | 앱 푸시 + 이메일 |
| 추가 조치 | 정산 계좌 변경 권고, 사업자 정보 악용 주의 | 비밀번호 변경 권고, CI/DI 유출 시 타 서비스 주의 |
| 보호위 신고 | 동일하게 72시간 이내 | 동일하게 72시간 이내 |

### 6.3 유출 규모 불확정 시

- 정확한 규모 산정에 시간이 걸리는 경우, **추정 최대치**로 보수적 판단
- 보호위 신고 시 "조사 중, 현재 추정 N명, 최종 확정 후 보고 예정"으로 기재
- 규모 확정 후 보호위에 후속 보고

### 6.4 유출 경로가 내부자인 경우

- 해당 계정 즉시 비활성화 (auth.users, app_roles)
- 증거 보전 특히 중요 — 해당 계정의 모든 접근 로그 보관
- 법적 대응 별도 검토
- 보호위 신고 시 "내부자에 의한 유출"로 경위 기재

### 6.5 오탐으로 확인된 경우

- 대응 프로세스 종료 기록 (GitHub Issue에 결과 기재)
- 가능성 통지를 이미 발송한 경우:
  - "조사 결과 유출이 확인되지 않았습니다"로 후속 안내 발송
  - 보호위에 기신고한 경우 "오탐 확인" 후속 보고

## 7. notification-worker 연동

사용자 통지 발송 시 기존 PGMQ + notification-worker 인프라를 활용한다.

### 7.1 통지 발송 플로우

```
통지문 확정
    ↓
PGMQ 큐에 메시지 발행 (대상 사용자 목록 + 통지 내용)
    ↓
notification-worker (Edge Function) 소비
    ↓
FCM 푸시 발송
    ↓
발송 결과 로그 기록
```

### 7.2 대량 통지 시 주의사항

- FCM은 한 번에 500개 토큰까지 멀티캐스트 가능
- 1,000명 이상 시 배치 처리 (PGMQ 메시지를 500명 단위로 분할)
- 발송 실패 토큰은 재시도 큐에 추가
- 모든 발송 결과를 로그로 남겨 통지 증빙으로 활용
