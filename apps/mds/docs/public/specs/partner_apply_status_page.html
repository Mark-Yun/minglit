Hierarchy Parent: — (top-level screen, no shell — outside StatefulShellRoute)

Purpose 신청서 제출 직후 또는 관리자 보완 요청 후의 사용자에게 현재 심사 상태를 알리고, 보완 요청 상태에서는 신청서로 되돌아가 수정할 수 있는 진입점을 제공한다. OnboardingState.pendingReview 또는 OnboardingState.needsCorrection일 때만 도달.
User journey Entry: PartnerApplyPage 제출 성공 직후 또는 router redirect. 앱 재진입 시 onboardingStateProvider가 pendingReview/needsCorrection으로 resolve되면 모든 경로에서 /apply/status로 강제 이동.
Exit: ① 승인 → hasPartner: onboardingState 변경에 의한 router refresh로 자동 /(PartnerHomePage)로 이동 — 이 화면에서는 별도 CTA 없음.
② 보완 요청 → 신청서 수정: "신청서 수정하기" → onboardingCoordinator.goToApply() → /apply.
③ 로그아웃: "로그아웃" 탭 → authRepo.signOut() → router redirect /login.
Background 파트너 신청은 관리자 수동 심사 + 서류 검토 단계가 있어 즉시 결과가 안 나온다 (영업일 기준 3~5일). 그 사이에 사용자가 앱을 다시 열어도 신청 마법사가 reopen되지 않게 별도 status 화면을 둠. OnboardingState enum 6 상태 중 이 화면은 2개 상태(pending / needsCorrection)만 커버.
Frequency 심사 진행 중 사용자가 앱을 열 때마다. 일반적으로 며칠 동안 지속, 승인/거절 시 자동 우회.

States

시각 변형 5종 — pending baseline · needsCorrection (admin comment 있음/없음) · loading · error. 첫 state 풀 리스트, 나머지는 변경분만.

State 종류 식별 기준: onboardingStateProvider AsyncValue (loading/error/data) + data일 때 OnboardingState 분기 (pendingReview vs needsCorrection) + application?.adminComment null 여부. router redirect가 다른 OnboardingState (loading 외 + needsApplication/draftInProgress/hasPartner)에서는 이 화면에 도달하지 않는다 — 도달했다면 곧바로 다른 라우트로 우회됨.

Cross-cutting interactions

사용자 액션 화면에 보이는 결과
"신청서 수정하기" 탭 (needsCorrection only) onboardingCoordinatorProvider.goToApply() → router.go('/apply'). 신청서 마법사가 기존 draft/제출 데이터로 prefilled되어 reopen. 재제출 후 status가 pending으로 돌아오면 다음 진입에서는 baseline으로 자동 전환.
"로그아웃" 탭 authRepo.signOut() await · auth provider invalidate · router refreshListenable 트리거 → !isLoggedIn 분기로 /login으로 redirect. 코드에 "GoRouter redirect가 signOut 중 widget tree를 변경하는 race condition 방지" 주석.
관리자 콘솔에서 application 상태 변경 이 화면이 active일 동안에는 자동 갱신 안 됨 (별도 push/realtime 미구현). 사용자가 앱을 재진입(provider rebuild)하면 onboardingStateProvider가 새 status로 resolve, 필요 시 router redirect로 다른 화면으로 이동:
· approved → hasPartner → / (PartnerHomePage)
· rejected → needsApplication → /welcome
· pending↔needs_correction → 이 화면 안에서 state만 swap.
시스템 back / 스와이프 back automaticallyImplyLeading: false. router redirect로 도달했으므로 stack에 보통 이전 항목 없음 → Android에서 종료, iOS에서 무반응. 위로 갈 곳이 없음.
다크모드 토글 scaffold gray ↔ dark surface · partner-primary 라이트(#6c3ce1) ↔ 다크(#9b7bec) swap · warning 토큰은 자동 매핑.

Global edge cases

  • 비로그인 상태에서 /apply/status 직접 진입 — router redirect의 !isLoggedIn 분기로 즉시 /login으로 redirect, 화면 보이지 않음.
  • 이미 hasPartner인 사용자가 /apply/status 직접 진입 — router redirect로 / (PartnerHomePage)로 우회. 이 화면 도달 안 함.
  • application이 null인데 onboardingState가 pendingReview/needsCorrection — application?.adminComment null-safe 접근(코드 주석 #180)으로 crash 회피. needsCorrection branch는 admin box 미렌더 (state 3), pending branch는 텍스트만 표시 (state 1).
  • onboardingState가 needsApplication / draftInProgress — 이 화면에 도달했더라도 router redirect가 즉시 /welcome 또는 /apply로 우회. 사용자에겐 짧은 깜빡임만 가능.
  • application.status가 'rejected' 또는 unknown — onboardingStateProvider switch 마지막 분기에서 OnboardingState.needsApplication으로 매핑됨. 이 화면 도달 안 함 — /welcome으로 redirect.
  • 관리자 코멘트가 빈 문자열 — adminComment != null는 true이므로 box는 그려지지만 본문 Text가 빈 줄. uncertain: 백엔드에서 빈 문자열 vs null 구분 정책.
  • signOut 실패 — await authRepo.signOut() 실패해도 화면에 별도 에러 표시 없음. auth state 무변화 → 사용자가 다시 로그아웃 시도 가능. uncertain: 실패 케이스에서 SnackBar 등 피드백 미구현.
