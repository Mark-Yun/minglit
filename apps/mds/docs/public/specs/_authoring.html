Spec Authoring Guide

화면 / 시트 / 컴포넌트 spec을 작성하는 모든 designer · agent를 위한 단일 참조. 아래 가이드를 한 번 읽고, 의문 생길 때 다시 돌아온다.

→ _template.html 열기 (복사해 새 spec 시작)

Filename convention

spec 파일명은 widget 클래스명의 snake_case. 디렉토리는 apps/mds/docs/public/specs/.

  • EventDetailPage → event_detail_page.html
  • PartyCreateWizardPage → party_create_wizard_page.html

Audience & perspective

Designer 관점에서 작성한다. 독자는 둘 중 하나:

  • (a) 화면을 처음 구현하는 implementer
  • (b) 구현이 spec과 일치하는지 검증하는 AI agent

사용자가 보고 / 하고 / 듣는 것만 적는다. 어떻게 구현하는가는 spec의 책임이 아님 — 구현 디테일은 /components 또는 widget-level 코드 주석에 둔다.

Spec status — design lifecycle

spec은 design artifact다. "코드가 spec을 따랐냐"는 spec의 책임 아님 — 그건 code review · CI · PR 링크의 영역. 따라서 Status field는 design phase만 추적한다:

🚧 디자인중작성 / 이터레이션 중. 변경 가능. 다른 design agent의 편집 안전.
✅ 디자인완료frozen, 최종 디자인. 구현 대기 중. code agent는 이 단계에서만 구현 시작.

라이프사이클: [new] → 🚧 디자인중 → ✅ 디자인완료. 리디자인이 필요하면 ✅에서 다시 🚧로.

구현 추적은 별도. Status를 변경하지 않고 History 섹션에 row를 추가:

  • Implemented in PR #123 (2026-05-15) — 코드 머지 시
  • code drift verify는 ad-hoc trigger (agent가 별도 요청 받아 수행)

Spec type — screen vs sheet vs component

템플릿은 SCREEN-first지만 sheet · component-tier spec에도 사용 가능. 변형 포인트만 조정:

Type변형 포인트
screen standard viewport (375×812). State 갤러리는 풀-page 변형.
sheet viewport는 sheet 너비 (343 or 375) × 자연 높이. State 갤러리는 sheet 컨텐츠 변형 (banner 유무, 빈 상태 등).
component /components/ 폴더에 배치. mockup이 컴포넌트 렌더 단독. Layout sub-anatomy가 곧 anatomy 본체. Global Behavior는 motion만. Reference는 사용처(where used) 위주.

Header의 breadcrumb · Role · Widget만 type별로 다르게 채우면 동일 구조 적용 가능.

Document structure

  1. 📍 Header — route / context metadata + Status
  2. 🎯 Overview — why this exists, user journey, background
  3. 🕐 History — spec change log
  4. 🧱 Layout — top-level blueprint + tree + spacing rules + REQUIRED sub-anatomy section per numbered region
  5. 🎨 States — stack of mini-tables (1 table per state). Header(state name + tag) → mockup(rowspan=6) + 6 aspect rows: 조건 / 사용자 액션 / 에지케이스 / 컴포넌트 / 토큰 / 노트
  6. 🔄 Global Behavior — cross-cutting only (motion, async, screen-wide edge cases)
  7. 📖 Reference — related screens. Components / Tokens는 STATES 내 mini-table에 분산 — Reference에서 중복 명세 안 함.

Sub-anatomy 자격 기준 (정량): 자식 위젯 2개 이상 + 정렬/간격 규칙 있음 → REQUIRED. 단일 atom (예: MinglitButton 1개) → 생략 가능, /components/ 참조.

Sub-anatomy 구조: 모든 sub-anatomy는 PARALLEL — Sub-anatomy ①, ②, ③ … 같은 level에서 평면 나열. 깊이를 늘리지 않고 region 개수만큼 섹션을 늘림.

Cross-cutting vs state-specific 판단 기준

분류기준 / 예시
cross-cutting
(Global Behavior)		 모든 state 또는 다수 state에서 동일하게 가능한 액션 / 이벤트.
예: OS back button · pull-to-refresh · scroll · dark mode toggle · 네트워크 끊김.
state-specific
(mini-table)		 그 state에서만 가능하거나 그 state 한정 결과를 내는 액션.
예: "구매하기" 탭 (eligible state에서만 enabled) · "다시 시도" 탭 (Error state에서만) · wizard step별 다음/이전.

States 종류 식별 가이드

Default · Empty · Loading · Error 4개는 default placeholder일 뿐 — 모든 화면이 이 패턴을 갖는 건 아니다. 화면이 가질 수 있는 시각 변형을 실제 코드 (provider state · route param · user state) 기준으로 enumerate한다:

화면 유형states
데이터 fetch 화면Default · Loading · Error · (Empty)
WizardStep1 · Step2 · … · Submitting · Success
Event detailadmission state 분기 (eligible · soldOut · applied · rejected · …)
Modal / Sheet진입 직후 · 사용자 입력 후 · async 진행 · 완료

Toolbar toggle states (Spec / Dark)는 별도 state 아님 — 모든 state에 적용.

Toolbar & chrome

Toolbar toggles (top-right, always visible):

  • Spec mode — annotations + numbered callouts overlay on viewports
  • Dark mode — flips viewport contents to dark tokens (chrome stays light)

All chrome (tokens · fonts · viewport frame · tables · annotations · callouts · type-specs)는 /specs/_spec.css에 산다. Screen-specific atoms (custom layout · brand-locked buttons)만 inline.

Standard viewport: 375 × 812 (iPhone 14/15 base) — _spec.css의 --spec-viewport-w / --spec-viewport-h로 정의.
