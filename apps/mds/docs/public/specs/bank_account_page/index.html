Purpose 파트너가 정산금을 수령할 은행 계좌를 등록·조회·수정한다. onboarding에서는 홈 todo의 canonical destination이며, 등록된 계좌가 있으면 마스킹된 요약(현재 계좌 카드)과 수정 폼을 함께 노출한다. 계좌 미등록 상태에서는 은행 선택, 계좌번호 입력, 예금주/사업자명 확인, 계좌 검증 상태를 한 화면에서 처리한다.
User journey Entry points: PartnerHome todo "계좌 등록" / 정산 화면 → "계좌 관리" 액션 / 정산 상세의 지급 실패 안내.
Exit points: 뒤로 가기 → 진입 부모로 복귀 / 검증 완료 저장 → 안내 메시지 + 화면 자동 갱신. Home에서 진입한 경우 bankAccountReady가 true일 때만 todo가 사라진다. bankAccountReady는 verified 또는 운영 승인된 manual_review_approved 상태를 의미하며, 단순 계좌 저장 여부(hasBankAccount)와 분리한다.
Background 밍글릿은 정산 후 등록된 계좌로 송금한다. 계좌 정보가 없거나 잘못되면 지급이 실패해 재지급 요청 경로로 빠진다. 본 화면은 그 원인을 사용자가 직접 해결할 수 있는 유일한 surface. 현재 Flutter는 자유 입력 후 바로 upsert하지만, canonical target은 은행 선택 sheet와 검증 status를 거친 뒤 정산 가능 계좌로 확정한다. 계좌번호는 카드 표시 시에만 마스킹(**** 1234)되고, 편집 폼에는 평문으로 채워진다 — drift 참고.
Frequency 입점 직후 onboarding에서 1회 등록. 계좌 변경 시 비정기적 재방문. payout FAILED 또는 검증 실패 발생 시 즉시 재방문.

Canonical onboarding contract

#3001 기준 이 화면은 정산 탭의 계좌 관리뿐 아니라 PartnerHome onboarding todo의 공식 도착지다. 아래 contract는 spec target이며, 현재 Flutter 구현과 다른 항목은 Reference의 구현 gap으로 추적한다.

Concern Canonical rule State transition
Home todo entry PartnerHomePage의 "계좌 등록" row 탭 → BankAccountRoute. Home stack은 유지. back은 Home으로 복귀. 정산 탭에서 진입한 경우 back은 SettlementPage로 복귀.
은행 선택 자유 입력이 아니라 bottom sheet single-select. 검색 + 주요 은행 quick list + 기타 은행 검색 결과를 제공한다. 은행 선택 전에는 저장 비활성 또는 validation error. 선택 후 sheet dismiss, field에는 bank display name이 들어간다.
계좌번호 입력 digits-only, 10-16자리. 붙여넣기 비숫자는 제거한다. 길이/형식 오류는 field-level error. 저장 전에는 서버 검증을 호출하지 않는다.
예금주/사업자명 매칭 사용자 입력 예금주와 partner legal/business name을 검증 결과에 같이 표시한다. 불일치면 verification_failed. 사용자는 수정하거나 수동 검증 요청으로 전환할 수 있다.
완료 조건 verified 또는 운영 승인된 manual_review_approved만 정산 가능 계좌로 본다. 완료 후 Home을 invalidate하면 "계좌 등록" todo가 사라진다. pending/failed/manual_review_pending은 todo를 유지한다.

Verification state model

Status Visible UI User action / fallback
not_started 미등록 form. 은행 선택, 예금주, 계좌번호 field와 저장 CTA. 모든 field valid → verifying.
verifying 저장 CTA disabled + inline spinner. 입력 field read-only. 안내: "계좌를 확인하고 있어요." 성공 → verified. 실패 → verification_failed. timeout → manual_review_pending 제안.
verified 현재 계좌 카드 + MinglitBadge(label: '확인 완료', compact: true, color: MinglitColors.success). 계좌번호는 last4만 표시. Home todo 제거. 정산 탭에서는 계좌 수정 가능.
verification_failed MinglitBadge(label: '확인 실패', compact: true, color: MinglitColors.error) + field-level reason. 예: 은행/계좌번호 불일치, 예금주 불일치, 휴면/해지 계좌. 수정 후 재시도 또는 "수동 검증 요청" outline CTA.
manual_review_pending MinglitBadge(label: '운영팀 확인 중', compact: true, color: MinglitColors.warning). 저장 CTA 대신 상태 확인/문의 CTA. Home todo는 "계좌 확인 중" subcopy로 유지. 운영 승인 시 todo 제거, 반려 시 failed로 복귀.

Global edge cases

  • 1원 인증 / 계좌 검증 미존재 — 본 화면은 계좌 정보를 그대로 upsert만 한다 (서버 측 검증은 별도 trust pipeline에서 처리되며 본 UI에 surface되지 않는다). "Verifying / Verified" 같은 인증 state는 현재 구현에 존재하지 않는다.
  • 마스킹 / 평문 비대칭 — AccountCard는 last4만 노출하고 나머지를 *로 마스킹하지만, AccountEditForm은 account_number를 평문으로 prefill한다. 어깨 너머 노출 위험 — 추후 보완 권고 (예: 폼도 마스킹 후 "변경" 탭 시 평문화).
  • partner == null 가드 — _loadAccount / _save 모두 partner null 시 early return. _save의 경우 setState로 _isSaving=true 후 partner null이면 finally에서 false 복귀 — UI 잠깐 disabled flicker 가능 (실측 필요).
  • 저장 실패 → SnackBar('저장 실패: $e') — exception toString을 그대로 노출. 운영팀이 사용자에게 stack trace 일부가 보일 수 있음 — error mapper 권고.
  • account_holder/bank_name 자유 입력 — 은행명은 enum/select가 아닌 자유 텍스트. 오타 → 송금 실패 root cause로 직결. 서버 측 normalize/whitelist 필요 (drift).
